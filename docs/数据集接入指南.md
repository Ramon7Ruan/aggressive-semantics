# 数据集接入指南

目标：把一份**你没见过的**数据集接进管线，且每一步可复查。

顺序永远是 **普查目录 → 看结构 → 写映射 → 导入 → 查台账**。
跳过第一步就会在几千个文件里瞎找；跳过第二步就会得到「导入成功但字段全空」。

> 下文统一写 `python -m discourse_kit.cli`。本项目自带 `./bin/dk`，两者等价，
> 它会自动挑一个装了依赖的解释器（先 `.venv`，再本项目隔离环境）：
>
> ```bash
> ./bin/dk survey data/raw/nbsdc/xxx.zip --probe 3
> ```

---

## 〇、下载之后第一件事：普查

```bash
python -m discourse_kit.cli survey data/raw/nbsdc/xxx.zip --probe 3
```

**zip 不用解压**：直接读中央目录，只取「路径 + 大小」，2.9 GB 的包几秒出结果。
输出包含五段，各自回答一个问题：

| 段落 | 回答的问题 |
|---|---|
| 格式分布 | 多少文件是 csv / log / docx，哪些管线能直读 |
| 目录形态 | 是否「一个主题一个目录」，分组发生在第几层 |
| 最大的 N 个文件 | 主表在哪（文本表通常体积最大） |
| 说明书候选 + 预览 | 字段含义以哪份文件为准（**直接贴出前 1800 字**） |
| 结论与警告 | 有没有表、缺不缺说明书、要不要写转换器 |

`--probe 3` 会对最大的 3 个表直接跑 `sniff`，一次拿到列名和建议映射。
但这一项**要求已解压**（压缩包内的表不能直接抽列）。

这一步能挡掉最常见的三类白费工夫：

- 整包只有 `log/cfg/docx` → 先写转换器，别急着写映射（survey 会直说「无法直接导入」）
- 中文名 zip 的乱码问题 → 已按 GB18030 回转，`数据说明.md` 不会变成一串乱码
- 总目录套了一层 → 分组层会自动下钻，不会因为「一级目录只有 1 个」而漏掉主题结构

### 下载注意

1. 页面需要**注册登录**才能看到下载入口；共享方式可能是「完全共享」或「审批后共享」，
   后者要提交用途说明并等待审核（以页面显示为准，不要按经验假设）。
2. 下载后**不要急着全量导入**。先看文件树：通常有一份 `*.md` / `readme` 说明字段含义，
   优先读它——它决定了映射怎么写。
3. 34160 个文件里绝大多数可能是日志与配置。先用 `survey` 按体积排序，文本表通常集中在少数几个
   大 `csv` 里。

## 二、接入流程

### 第 1 步：看结构

```bash
python -m discourse_kit.cli sniff data/raw/你的文件.csv
```

输出会告诉你：编码、分隔符、全部列名、采样非空率、建议映射、**缺哪些必填字段**。

编码判断不是靠猜：依次尝试 `utf-8-sig / utf-8 / gb18030 / gbk / big5 / utf-16`，
按「能否整段解码 + 中文字符比例」打分。只读前 1 MB，2.9 GB 的文件也不会读满内存。

### 第 2 步：写映射

```bash
python -m discourse_kit.cli sniff data/raw/你的文件.csv \
    --write-mapping data/mappings/你的数据集.yaml
```

然后**人工核对**生成的 YAML。重点看三处：

| 项 | 常见坑 |
|---|---|
| `doc_id` | 用了「帖子ID」而不是「评论ID」→ 全帖只有一个 ID，导入后大量重复 |
| `unit` | 数据集往往没有这一列，用 `unit_default` 指定；论点级数据填 `argument` |
| `text` | 映射到了「标题」而不是「正文」→ 中文字符占比会异常低（质量检查 V6 会警告） |

映射格式与规则见 `data/mappings/example.yaml`。

### 第 3 步：导入

```bash
python -m discourse_kit.cli run --file data/raw/你的文件.csv \
    --mapping data/mappings/你的数据集.yaml
```

先加 `--limit 2000` 试跑，确认字段对得上再全量。

### 第 4 步：查台账

打开 `data/processed/metric_coverage.csv`。**这一张表决定你能不能做研究**：

- 若 `G1_intensity`、`D2_absolutism` 等核心指标 `status=ok` 且 `coverage` 高 → 可以往下做
- 若大量 `skipped_missing_field` → 数据集缺字段，不是代码问题，别去改代码
- 若 `no_valid_value` 集中在 MATTR / 论证密度 → 文本太短，说明这份数据是「短评论」型，
  长文本指标整体失效，必须在方法节披露

## 三、字段优先级

拿到数据集后，按这个顺序确认字段是否存在——**越靠前越决定研究能否成立**：

| 优先级 | 字段 | 缺了会怎样 |
|---|---|---|
| 1 | `text` + `thread_id` + `doc_id` | 什么都做不了 |
| 2 | `unit`（或 `unit_default`） | 无法区分主楼与回复，长度比较全部失真 |
| 3 | `topic_title` | 无法编码话题类型 → H1–H4、H6–H8 全部失效 |
| 4 | `stance` | 只能靠词典推立场，可靠性大幅下降 |
| 5 | `floor_no` + `posted_at` | 「讨论劣化」（H8）与时间演化无法检验 |
| 6 | `author_id` | 参与集中度、重复发言者分析不可用 |
| 7 | `reply_count` / `view_count` | 只影响控制变量，不影响主结论 |

## 四、已知的坑

1. **论点级数据不是对话数据。** 辩论文档常是「论点 + 论据」的扁平结构，
   没有楼层、没有回复关系。这种数据能算话语形态指标，但算不了「帖内演化」。
   `sniff` 之后先看有没有 `floor_no` 与 `parent_id`，没有就不要指望 H8。
2. **自带标签不等于可信标签。** 数据集作者用 NLP 生成的「立场」「论据类型」，
   精度未知。把它当**变量**用可以做，当**金标准**用不行——至少抽 100 条人核，
   报告里写明一致率。
3. **多源混合会带来平台差异。** 知乎长文、微博短评、豆瓣小组的语气差别极大。
   若数据集混了三源，必须把 `platform` 映射出来，否则你测到的是平台差异而不是话题差异。
4. **不要用 `head` 看文件结构。** 2.9 GB 的文件前面几行没有信息量；
   也不要用 `head -25` 判断 robots.txt 这种只有 31 行的文件——本项目就因此把
   「全站禁止」误判成「允许」过一次。

---

## 五、如果数据集不够用

管线本身不依赖任何特定来源。补齐数据有两条路：

- **补公开数据**：换成维基百科讨论页 dump、Reddit 存档等（需确认许可与 robots）
- **自采**：`adapters/base.py` 定义了采集适配器协议（列表页 / 详情页 / 解析），
  实现一个即可接入。自采前必读 `discourse_kit/fetcher.py` 的 robots 守卫与限速实现。

无论哪条路，下游 `schema → metrics → export → report` 一行都不用改。
